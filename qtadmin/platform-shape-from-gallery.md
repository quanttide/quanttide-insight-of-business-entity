# 从 gallery 反推 qtadmin 平台形态

记录于 2026-11-12。整理 `quanttide-gallery-of-business-entity` 的 qtadmin 板块时，从其信息组织方式反推要研发的 qtadmin 平台应是什么形态，经创始人认可。此处的平台指 `apps/qtadmin` 要研发的产品，非 gallery 文档库本身。

## 六个职能域即产品模块

gallery 的目录结构（组织、人力、沟通、议事、产品、资产）不是文档分类习惯，而是平台的信息架构：新文档「注册进 toc」的惯例，对应平台即模块的注册与上架机制。gallery 是需求规格的精简版，目录树基本等于产品的 IA。

## 心脏是治理流程引擎

gallery 里沉淀的做法几乎全是有状态、有角色、有留痕的流程：

- 两级认证：公司核实事实 → 联盟表决标准
- 评审制：初审 + 终审、结论留痕
- 立法信息反馈：新制度 → 代表大会审议
- 证明材料分层发放

这些不是展示型数据，是 workflow。平台核心能力应是流程编排 + 审计轨迹，而不是 CRUD 看板。

## 权限模型来自三权分立

代表大会 = 议会、秘书处 = 政府、顾问团 = 法院——这个建模落到平台上就是角色与权限体系：谁发起、谁审议、谁终审。「公司不能成为联盟的仲裁者」这类制衡规则要成为系统的硬约束，而不是靠自觉。

## 人和 AI 是同一操作面的两类用户

惯例写成可被程序遵循的流程（如众包三步上线：quanttide-crowd 更新 profile → AI 上线 qtclass → lite 发新 patch），说明平台要同时暴露给员工和 AI agent 执行。接口设计原则：流程即 API。

## 对内管理面

服务创始人、秘书处、部门负责人，管公司自己的运转（群聊、会议、绩效、议事）；与量潮课堂、众包等应用层对外产品分属两侧。

## 待定问题

在「领域层 / 应用层」分层模型中，qtadmin 是应用层产品（把沟通云、议事云等领域能力组装起来做内部管理），还是独立于分层之外的管理控制台？从「对内管理面」的措辞看更像后者，待创始人拍板。这决定它是自建模块还是编排领域能力。
