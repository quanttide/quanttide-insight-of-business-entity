# 评审环节可行路径

解决「事情分下去没有明确评审人、职责回流创始人」的操作路径。素材来自业务日志中的真实实践（06-09、06-15、06-20、07-09、07-31、08-11）。

## 四步路径

### 第一步：摩擦盘点——一次摩擦一条标准

从高频摩擦开始，复盘四问：谁缺位、缺什么标准、标准怎么写、进哪本册子。标准要素：条件（什么情况适用）+ 动作（做到什么算过）+ 证据（怎么验证）。

已有摩擦案例库：

- HR 单独补发邮件（08-11）：职责回流创始人
- PM 离职客户无人回复、创始人救火（06-09）：交接断裂在 HR 环节，离职优先级太低
- 新人沟通摩擦（06-20）：复盘成沟通章程

### 第二步：责任划分——评审人怎么定

- 区分基本责任与成长责任（06-09）：基本责任是职责底线，成长责任是发展义务
- 权责排他：一个事项一个负责人，私有信息广播公开
- 通过拒绝划分边界：明确不做什么（如 HR 不负责技术文档）
- 角色槽位：任务类型 → 默认评审人（常规=直接指导者、政策类=秘书处、重大=创始人）

### 第三步：评审动作——怎么评

- 对照执行契约检查：交付物、截止时间、范围
- 评审结论必留痕：通过 / 打回（附原因）
- 评审即制度修订：评审打回暴露的共性问题 → 修订标准（06-15：评审 PR 拒绝后立 DevOps 章程）
- 验收复现检查：项目交付后有没有人复现、有没有人接棒（07-31）

### 第四步：闭环跟踪——怎么保证不回流

- 事后跟踪优先：确保落实而非重复安排（06-20）
- 责任链条定期检查：有没有人对交付负责（07-31）
- 秘书处调配 + 甲乙方交付意识（07-09）
- 进度广播公开：入离职进度群广播，未来用系统替代（06-09）

## 关键认知

- 评审打回是制度的输入，不是对个人的否定——用客观证据强化责任心，制度鼓励承担、不过度惩罚（07-22）
- 评审人揽责是权威来源：责任集中在评审人手中，评审才有分量（见 `governance-authority`）
- 摩擦区分偶发与结构性：偶发摩擦不立制度，结构性缺位才立（见 `friction-driven-institutionalization`）

## 边界

- 揽责的前提是能对下级负责，否则揽责变揽权
- 信息结构先于激励：评审人给不了明确回复，先检查信息是否透明
- 评审是执行闭环的一部分，不是事后补丁

## 产品化

实践是行为，产品是把行为结构化的载体——四步路径映射为四个产品模块：

| 实践步骤 | 产品模块 | 核心功能 |
|---------|---------|---------|
| 摩擦盘点 | 摩擦登记与标准生成器 | 复盘四问引导表单、AI 辅助生成标准草稿（条件+动作+证据）、摩擦库结构化存储（偶发/结构性标记） |
| 责任划分 | 角色与责任管理 | 角色槽位表（任务类型→默认评审人）、基本/成长责任字段、权责排他校验、「不做什么」边界清单 |
| 评审动作 | 评审工作台 | 执行完自动派发评审、对照契约 checklist、结论结构化（通过/打回+原因）、打回原因自动聚类 |
| 闭环跟踪 | 责任链看板 | 落实状态（拒绝重复安排）、责任链视图、进度广播（系统替代人）、制度外例外自动上升 |

### 产品化的飞轮：评审即制度修订

最有价值的产品化点不是评审动作本身，而是打回数据的复用：评审打回 → 聚类分析 → 共性原因 → 建议修订标准 → 标准库更新 → 下次评审按新标准。系统自动发现共性，制度修订从人工复盘升级为数据驱动。

### 数据模型（复用执行云任务模型）

- Task（已有）：双重属性 + 角色槽位 + 状态流转，新增评审节点状态
- Friction（新）：摩擦登记（场景、缺位者、缺的标准、偶发/结构性）
- Standard（新）：评审标准（条件、动作、证据、来源摩擦、版本）
- Review（新）：评审记录（评审人、结论、原因、关联任务与标准）

### 落地顺序（对齐 execute 演化）

- 近期：评审闭环 MVP——角色槽位分配、评审节点、留痕、摩擦登记表（表单/文档承载，跑真实案例）
- 中期：质量飞轮——意图澄清、标准库、打回聚类分析→制度修订建议
- 远期：系统权威——制度库自动执行、责任链看板、跨云协同
