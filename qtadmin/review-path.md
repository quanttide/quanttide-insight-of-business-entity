# 评审环节可行路径

解决「事情分下去没有明确评审人、职责回流创始人」的操作路径。素材来自业务日志中的真实实践（06-09、06-15、06-20、07-09、07-31、08-11）。

## 四步路径

### 第一步：摩擦盘点——一次摩擦一条标准

从高频摩擦开始，复盘四问：谁缺位、缺什么标准、标准怎么写、进哪本册子。标准要素：条件（什么情况适用）+ 动作（做到什么算过）+ 证据（怎么验证）。

已有摩擦案例库：

- HR 单独补发邮件（08-11）：职责回流创始人
- PM 离职客户无人回复、创始人救火（06-09）：交接断裂在 HR 环节，离职优先级太低
- 新人沟通摩擦（06-20）：复盘成沟通章程

### 第二步：责任划分——评审人怎么定

- 区分基本责任与成长责任（06-09）：基本责任是职责底线，成长责任是发展义务
- 权责排他：一个事项一个负责人，私有信息广播公开
- 通过拒绝划分边界：明确不做什么（如 HR 不负责技术文档）
- 角色槽位：任务类型 → 默认评审人（常规=直接指导者、政策类=秘书处、重大=创始人）

### 第三步：评审动作——怎么评

- 对照执行契约检查：交付物、截止时间、范围
- 评审结论必留痕：通过 / 打回（附原因）
- 评审即制度修订：评审打回暴露的共性问题 → 修订标准（06-15：评审 PR 拒绝后立 DevOps 章程）
- 验收复现检查：项目交付后有没有人复现、有没有人接棒（07-31）

### 第四步：闭环跟踪——怎么保证不回流

- 事后跟踪优先：确保落实而非重复安排（06-20）
- 责任链条定期检查：有没有人对交付负责（07-31）
- 秘书处调配 + 甲乙方交付意识（07-09）
- 进度广播公开：入离职进度群广播，未来用系统替代（06-09）

## 关键认知

- 评审打回是制度的输入，不是对个人的否定——用客观证据强化责任心，制度鼓励承担、不过度惩罚（07-22）
- 评审人揽责是权威来源：责任集中在评审人手中，评审才有分量（见 `governance-authority`）
- 摩擦区分偶发与结构性：偶发摩擦不立制度，结构性缺位才立（见 `friction-driven-institutionalization`）

## 边界

- 揽责的前提是能对下级负责，否则揽责变揽权
- 信息结构先于激励：评审人给不了明确回复，先检查信息是否透明
- 评审是执行闭环的一部分，不是事后补丁
