# 门槛是体系最大的 feature

> 证伪时限：2027-05（到期重审）
> 来源：2026-11-02 群聊实录（门槛领悟、WorkBuddy 工作流、实训基地复制指令）；实证材料为 auth-pay 开发清单的可行性评审（roadmap 仓 `qtclass/product/auth-pay.md`，2026-11-02）
> 预测：把「接入一个系统」的入门任务成本打到非技术者可独立完成之后，交付主通道从上门实施变为「给链接给任务」。可被实训基地全员复制该流程的汇总报告证伪（独立完成接入任务的比例不足以支撑客户自助接入）；若真则咨询与交付的资源从实施人力转向工作流与预制菜的打磨。

## 一个对象，五条线

体系最大的 feature 是让非技术的人迈过技术的门槛。五条线都在这一个对象上干活：

- **云 = 预制菜**：直接提供，不想懂技术的人开箱就吃
- **课堂 = 把人教会**：教到能自己动手
- **VIP 学员 = 往我的水平收敛**：不满足于跨门槛，走到设计者身边
- **一般学员 = 跨过门槛就够**：会用、会改、会接
- **咨询 = 把技术推广到企业里**：组织级的跨门槛

## 门槛怎么降下来

云是低成本的失败腌出来的：架构自下而上一层层堆，集成阶段海量实验——量潮云就是软件届的预制菜。

降门槛的工作流（2026-11 实测）：

1. 平台全部分解成一个个子系统开源，AI 读写任何一个子系统都省力
2. 子系统 GitHub 链接喂给 WorkBuddy：免费云电脑拉代码，免费模型做方向不确定的实验
3. AI 反思为什么失败，把上下文整理成文档
4. 踩完坑才进本地正式开发

云端专门踩坑，本地只做踩过坑的活：任务窗口变多、注意力省了、质量提前提了，非技术者也能上手。失败是原料不是损耗——不需要成功，做了就行，失败报告越多，越知道怎么改进。

**实证**：把三个仓库链接加一个真实任务（给量潮课堂接入账号系统和支付系统）交出去，产出的开发清单逐条核对三仓代码，接口、路径、字段几乎全对。单个入门任务已经跑通，剩下的问题是它能不能规模化——那是汇总报告要回答的。

## 点名：上门实施判死缓

客户也能用这个方式接入我们写好的系统——交付从「我们上门实施」变成「给链接给任务，客户自己跑」。这个玩意要上生产，对整个行业的研发成本是核爆炸式的。
