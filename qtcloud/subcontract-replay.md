# 分包复现跨出技术侧：众包云规格应取两处交集

> 证伪时限：2026-12（到期重审）
> 来源：journal qtclass 2026-09-10（课题作者发明完整分包制度：设计 PR 竞争接取、四方评审 + CI、30 天释放、仪表盘记分）、2026-09-24（商务入门题触发分发三问：个人做还是上任务网、是否自己对接客户、走 PR 还是交接）；承接「复现即成熟」（量潮云体系总述）与[制度生成的社会路径](../qtclass/institution-generation-path.md)。

## 感知现实

9-10，技术侧一位课题作者在真实需求（课题功能超过单人产能）压力下，独立发明了任务拆解与分级、竞争接取、多方评审 + CI、超时释放、自动记分的完整制度。

9-24，众包第一单转为商务入门题不到一天，新秘书提出三点确认：个人案例任务之外，是否把后续需求放上实训基地众包任务网「给商务意向的同学们一起做」、是否需要大家自己与客户对话交流、交付走 PR 还是与副主席交接。三个问题本质是同构四问：任务发给谁、以什么门槛认领、交付怎么评审、归口在哪里。

## 理解抽象

制度复现沿「任务量超过单人产能」的痛点跨职能扩散，与岗位性质无关——复现的首先是问题序列，其次才是解决方案。技术侧已把问题序列走完一遍并长出制度，商务侧正在重走同一序列。两处复现的交集即普适要素，差集即职能特有要素：技术侧没有「客户对话权限」，商务侧没有「CI 流水」。

## 预测

**我们预测：众包云的第一版产品规格将来自技术侧与商务侧两处独立复现的合并，任何一处的单独沉淀都不足以成为规格——把 9-10 的分包机制原样搬进众包云是错的。**

- 可证伪：若商务第一单全程未出现分发、认领、归口的制度讨论（直接指定单人做完），或商务侧长出与技术侧完全不同构的机制，则预测错误
- 若真：众包云产品化前应等商务第一单跑完，采集两处复现的交集作为规格骨架，差集（客户对话权限、交接归口）作为商务侧扩展；现在只搬技术侧机制会漏掉商务侧特有要素
- 点名：预言「拿 9-10 分包机制直接产品化」这条路死亡——第三处复现（如运营、内容岗位出现同类分发问题）出现之前，规格窗口不关闭但也未定型
