# 工作云的孵化与毕业

> 命题：主站是孵化器，不是归宿——领域在主站里长出闭环，毕业条件满足就分解为独立产品线。拆分的信号是业务信号（出现了独立的诉求方与闭环），不是代码洁癖；而拆分的成本，要在孵化期就预付（接缝与接口）。

来源：与 AI 的架构对话（2026-09-08，examples/studio 原型演进与 Artifact 接口重构现场）+ journal qtcloud/2026-09-07（河床）+ qtadmin 领域去向表先例 + specification/work 概念语言入册

## 一、分解的三个信号

工作云（qtcloud-work）从 qtcloud 主站分解出来，不是拍脑袋，是三个信号同时亮起：

- **概念语言先入册**：Workspace / Task / Workflow / Artifact 已定义进工程标准（specification/work）——领域语言先于仓库迁移，是 devops / agent / meta 三个先例共同走过的顺序
- **验证场景成形**：招聘政策接力、A 校项目方案——工作云有了自己的验收场景，不再依附门户的功能列表
- **独立子域就位**：cowork.cloud.quanttide.com 已规划，与 delib.cloud、data.cloud 平级

先例支撑：qtadmin 领域去向表里，human / connect / asset / business / knowl 各领域都在主站孵化、闭环后拆分为 qtcloud-{领域} 产品线仓库。

## 二、毕业条件先于拆分存在

孵化最容易失控的方式是无限期孵化（主站长成巨石）与过早拆分（带着空壳建仓）两头摇摆。解法是**先写下毕业条件，再开工**：

- qtcloud-work 的毕业条件：**首个 Workspace 闭环跑通**——河床三步旅程或招聘政策接力，真实数据、真实闸门、真实的验收记录
- 不满足就继续孵化：差的是真实数据源、持久化、云端点，那就补这些，不拆仓库
- 满足即拆：仓库带着一个能跑的产品出生，而不是带着一个空壳

两条禁令互为镜像：不被平台建设诱惑（别超前建），也不被拆分洁癖诱惑（别零消费者就抽象、就分仓）。

## 三、接缝预付：拆分成本在孵化期结清

拆分那天是搬家还是重写，取决于孵化期有没有埋好接缝：

- **依赖抽象而非实现**：工作流依赖 Artifact 接口（能吸收修订并推进版本），不依赖具体文档——文档云将来带走 Doc，工作流零改动
- **文件按领域切**：models/ 里 document / task / workflow / workspace 各归其位，拆分沿文件边界走，不做代码考古
- **领域知识跟随领域走**：work 概念语言（specification/work）届时随域迁入工作云的文档库，对齐 devops / agent / meta 的先例

一句话：孵化期多写一个接口，毕业那天少搬一次家。

## 与其他洞察的关系

- [dogfooding-as-strategy](dogfooding-as-strategy.md)：孵化期的营养来源——工作云的闭环先跑在量潮自己的工作流上，内部用户是第一批验收者

## 使用姿势

1. 每个孵化物开工前写下毕业条件——没有毕业条件的孵化是无限期占用主站
2. 拆分信号只认业务信号：独立的诉求方、独立的闭环、独立的概念语言；代码变多不是信号
3. 孵化期预付接缝：跨对象依赖走接口、文件按领域切，让「拆分 = 搬家」

---

**一句话**：主站养领域，领域毕业建仓库——毕业条件写在开工前，接缝埋在孵化期。
