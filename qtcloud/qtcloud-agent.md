# AI 信誉系统：让建议权可以被度量

> 来源：AI 席位设计（见 intro/power-capped-by-responsibility.md）的工程化追问——「建议被采纳的频率与质量就是 AI 的票数」如何变成系统。本篇是 insight 层的制度设计与 qtcloud 执行云研发之间的桥：信誉系统应作为执行云的原生模块，而非事后补丁。

## 问题定义

AI 在这个组织里只有建议权（无投票权），信誉是建议权体系里唯一的货币。但目前的信誉是**隐式的**——它存在于创始人的头脑里（「这个 AI 的提炼不错」「上次判断错了」），不可查询、不可积累、不可跨场景携带。

一个不可见的信誉体系有三个缺陷：

1. **无法积累**：AI 换了版本、换了场景，信誉清零重来——重复犯错无法避免
2. **无法流通**：A 业务线对某个 AI 的信任无法被 B 业务线复用，每次合作都从零建立
3. **无法制衡**：AI 自己不知道自己的信誉状态，无法自我校正；人也无法基于数据而非印象分配 AI 任务

所以问题等价于：**如何把「建议 → 采纳 → 后果」的链条变成可记录、可计算、可查询的数据？**

## 信誉系统设计

### 核心数据结构：建议记录（Suggestion Record）

每一次 AI 建议生成一条记录，字段：

```
SuggestionRecord {
  id                    // 建议唯一标识
  agent_id / version    // 哪个 AI 的哪个版本（版本可比较、可回溯）
  context               // 建议产生的场景（群、议题、任务、关联文档）
  content_digest        // 建议内容摘要（含依据：引用了哪些章程/手册/日志）
  action_taken          // 采纳结果：采纳 / 采纳并修正 / 部分采纳 / 拒绝 / 待定
  modifier              // 修正者与修正内容（人改了什么——这是质量信号的核心）
  outcome_link          // 后果链接：采纳后产生的交付/决议/文档
  responsibility_owner  // 责任人（采纳建议的人为后果负责——与权限原理一致）
  timestamp
}
```

关键设计：**action_taken 不是二值的**。「采纳并修正」是最有信息量的状态——它同时说明建议有价值（值得采纳）和有缺陷（需要人修正），修正内容本身就是对 AI 的针对性训练数据。

### 信誉计算：三个维度而非一个分数

不做单一评分（单一分数会被博弈），按维度分开：

1. **采纳率**（acceptance rate）：采纳 / (采纳+拒绝+待定)——反映建议的总体质量
2. **修正率**（modification rate）：「采纳并修正」占采纳的比例——反映建议的「可用距离」：低修正率 = 拿来即用，高修正率 = 方向对但功夫不够
3. **后果质量**（outcome quality）：采纳后产出的验收结果（交付是否通过、决议是否被后续推翻）——这是慢变量，也是最硬的指标：**建议的真价值在后果里，不在当下**，与「验收是基本能力」「考核函数」的组织逻辑一致

分维度的一个直接好处：**不同场景看重不同维度**。事实校验类建议看采纳率，方案类建议看修正率趋势（应逐次下降），战略类建议只看后果质量——慢变量急不得。

### 信誉的边界：分场景、分版本、会过期

- **分场景**：给 journal 整理的信誉 ≠ 给课题评审的信誉 ≠ 给代码生成的信誉。信誉矩阵是「agent × 场景」的表，不是一条总分。跨场景只携带「元信誉」：修正率的下降趋势（这个 AI 会不会从错误中学习）
- **分版本**：模型升级 = 新的 agent_id。旧版本的信誉不继承，但保留为参照——**新版本必须在低风险场景重新赚信誉**，这和人类成员「权随能授」完全同构
- **会过期**：信誉记录设时间衰减。半年前的高采纳率不能为今天的错误建议背书——与组织的快照式时间观一致（信任 HEAD，不信任 history）

### 与人类成员信誉的同构性

人类代表也有信誉问题（评审的公允性、提案的质量），只是靠面对面场合的声誉机制运行。这套系统设计对人类同样适用：**代表大会的评审记录、代表的提案-决议链，可以用同一种数据结构记录**。这带来一个长期可能：AI 与人类的信誉在同一个系统里可比——「按被制度化的程度发席位」就有了统一度量。

## 落地路径：挂在执行云的哪个位置

按 qtcloud 的演化阶段（见 qtcloud.md 的三个矛盾），信誉系统不是独立产品，是**验收机制（矛盾一）的 AI 侧延伸**：

1. **0.2 阶段（信任与验收）**：先做最小版——执行云里 AI 产出的任务/文档，人类验收时的动作（通过/修改后通过/驳回）天然就是 action_taken 数据。**不需要新建流程，只需要把验收动作结构化记录**。招聘考核案例跑端到端时同步跑
2. **0.3 阶段（运行时契约）**：契约校验的数据可以反哺信誉——AI 产出符合契约的比例是客观的采纳率变体。修正率通过 contract 与 blueprint 的迭代循环自动沉淀
3. **0.4+ 阶段（专家系统化）**：跨场景信誉矩阵成型，AI 席位进入议事云时，信誉数据就是它的「履历」

与「假设前置化」「考核函数」（06-28、06-30 日志）的关系：信誉系统是它们的个人化延伸——考核函数度量单次任务，信誉度量累积表现；假设前置化的判定记录就是建议记录的前身。

## 设计原则（从权限原理导出）

1. **建议可度量，决定不可度量**：系统记录建议的质量，但「采纳与否」的决定权数据属于人——信誉系统不变成 AI 的绩效监控（那是「有罪推定」的老路，qtcloud-execute.md 里刚否决过）。系统的姿态是**帮助 AI 变得更好，而非监工**——与「系统澄清在前、员工执行在后」的产品哲学一致
2. **修正内容是核心资产**：人对建议的每一次修正都应沉淀为 AI 的改进输入（feedback → training/规则更新），否则信誉只是记分牌不是成长引擎
3. **责任链不断**：每条采纳记录带责任人——信誉数据永远不改变「人为后果负责」的权限原理
4. **透明与对称**：AI 可以查询自己的信誉（分维度、分场景），如同人类代表可以查询自己的评审记录——**信誉系统对被记录者透明，是被记录者被制度认真对待的标志**

## 一句话

信誉系统的本质是：**把「建议权体系」从靠印象运行的人际机制，变成有数据结构的制度组件——AI 因此可以积累信誉、携带信誉、用信誉换取更大的建议影响力，但永远换不来投票权，因为数据填不了责任的位置。**
