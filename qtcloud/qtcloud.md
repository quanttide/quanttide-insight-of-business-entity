# 量潮云形态演化的关键节点与难点

基于量潮云意图（`data/intention/qtcloud/qtcloud.md`）的形态演化路线，分析从门户到 CoWork/WorkBuddy 形态的关键节点、难点与顺序建议。

## 关键节点

演化路线中有三处质变点，决定成败：

- 0.1 到 0.2：从逛工具到派活，交互范式第一次切换。系统第一次接管流程记忆，任务拆解若不可靠，信任在第一天崩塌
- 0.2 到 0.3：从设计时到运行时，最大的技术质变。协作目录从告诉你怎么连变成替你跑，AI 输出从建议变成交付物，错误成本陡增
- 0.4 到 1.0：从个人到组织，从效率问题变成治理问题。多 Agent 并行出错谁负责、流程复用的权限边界，不是纯技术能解决

其中 0.2 到 0.3 是承重墙：这是 CoWork 模式与聊天工具的本质区别，而各云目前都是独立应用，离被任务调度执行有工程量差距。

## 难点

- 信任的迁移：意图说人只需要下指令和验收，但信任从确认迁移到验收需要系统给出确定性。信任机制目前是客服云的内容，实际应随任务工作台一起落地，而不是最后补
- 契约从设计时变成运行时校验器：Event 与 Contract 目前是注册表，0.3 起必须成为验收标准，交付物是否符合契约决定人能否放手。契约既标准化又灵活的度很难拿
- 隐式经验的显式化：专家生态的前提是把会做变成能教，SOP 与知识库逐条沉淀是长期的苦功夫，不是技术问题而是认知问题
- 各云执行端点逐个落地：议事云是对话、数据云是工程平台，形态各异，长出能领任务、能汇报、能交付的执行层是纯工程量
- 业务与平台演化的节奏匹配：云从业务中长出来，难点是克制——不被平台建设诱惑，让业务推进节奏决定产品演化节奏

## 顺序建议

最危险的是在信任底座和真实业务缺失时先建平台。应先在一个真实业务中跑通端到端闭环（如招聘政策案例：任务输入、拆解、多模块接力、交付草案、验收），用这一个案例同时逼出任务拆解、契约校验、验收机制三块能力，再横向复制到其他云。
